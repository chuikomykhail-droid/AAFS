# План: прогноз воздушных тревог в Украине (MVP)

## Контекст задачи

- Тестовое задание: мини pet-проект на Python, анализ временных рядов воздушных тревог в Украине.
- Дедлайн: понедельник, 12.10.2026, 23:59 по Киеву.
- Требования: работать с самыми свежими данными, оценивать решение на последнем периоде, не допускать утечки. Ни обучение, ни входы модели не используют ничего, что появилось после момента прогноза.
- Что сдаём: ссылку на GitHub-репозиторий с рабочим кодом, полный лог работы с ИИ (чат планирования, сессии Claude Code и Antigravity), рефлексию (~100 слов).
- Проверяющие в первую очередь оценивают процесс: итерации, пойманные ошибки ИИ, обоснованные решения.

## Данные

- Источник: `github.com/Vadimkin/ukrainian-air-raid-sirens-dataset`, файл `datasets/official_data_en.csv`. Время в UTC, лицензия MIT. Данные собираются процессором из Telegram-канала `air_alert_ua`.

## Правила работы (для ассистента в Claude Code / Antigravity)

1. **Не предполагать структуру данных.** Сначала показать реальные колонки, `head()` и `value_counts()`, и только потом писать логику.
2. **Дедупликация — до любых подсчётов.** Любая статистика, посчитанная на данных с дубликатами, неверна.
3. **Признаки — только из прошлого.** Любой признак есть функция от истории строго до момента `t`. Нельзя использовать `rolling(center=True)`, `bfill`, интерполяцию, нормализацию, обученную на всём датасете.
4. **Состояние в момент `t` считается по точным временам интервалов**, а не по часовым корзинам. Корзина `[t, t+1ч)` содержит будущее.
5. **Решения о структуре данных** (пороги, клоны, маски) принимаются по обучающему периоду и **не подбираются по метрикам.** Параметры, которые определяют саму целевую переменную, фиксируются заранее.
6. **Тестовый период не трогаем.** Гиперпараметры и набор признаков не подбираются по результатам на тесте.
7. **Каждое нетривиальное решение записывается в `DECISIONS.md`:** что решили, почему, какие были альтернативы. Пойманные ошибки ИИ тоже записываются.
8. **Цифры сверяются со справочной таблицей в `DECISIONS.md`.** Если повторный подсчёт расходится, сначала разобраться в причине.
9. **Справочные данные проверяются.** Списки соседства и подобное сверяются с геоданными, а не генерируются по памяти.
10. **Сложность наращивается по шагам.** Новый шаг начинается только после того, как текущий работает и проверен.
11. **Работа со временем:** время переводить в числа только явно, через `.dt.as_unit('s')` или `Timedelta`; не использовать `.astype('int64')` и `.view('i8')` для дат (в pandas 3 единица по умолчанию может быть микросекундой). Для этого есть `alerts.timeutil.to_sec` / `from_sec`.
12. **Признаки читают историю только через `AlertHistory` (D16, D21).** `FeatureBuilder` получает только её, сырых таблиц у него нет. Информация на момент `t` — то, что было записано к `t`. Флаг `uncertain`, маски (а) и (б), концы эпизодов — ретроспективные, в признаки они не идут. Каждый признак автоматически проверяется `tests/test_knowledge.py`: значения по «знанию на момент среза» должны совпасть со значениями по полным данным.
13. **Охват — только через `select_scope()`, константы — только в `config.yaml`, модули не пишут файлы.** Запись на диск делают `pipeline.save_all()` и `scripts/run_all.py`.

### Этап 3. Сетка и целевая переменная — выполнено

**Как сделано:** `src/alerts/grid.py`, решения и цифры — D17, сводка — `reports/stage3_summary.md`, таблица — `data/grid.parquet` (строится `run_all.py`, в git не входит). Сверх плана: строки нет и тогда, когда отбой не виден в реальном времени (`held_open`, 8 строк). Выбраны горизонты 1, 3, 6, основной — 3.

**Исходное задание:**
- Строки `(единица, t)` с шагом в час, только для моментов, когда в единице тихо.
- Первая неделя (2025-11-07 – 2025-11-14) служит разогревом признаков, строк для неё нет.
- «Тихо» в `t` — по эпизодам: строки, где `t` попадает в склеенную паузу своей единицы, не создаются (D12).
- **Строки не создаются** (D10, «Семантика для этапа 3»):
  - если `t` в любой маске;
  - если окно `(t, t+h]` задевает маску (в) или (г): у них начало — не событие, метка неизвестна, а отбор зависит только от времени, но не от исхода. Сюда же входит `t + h > data_end`.
- Окно, которое задевает маску (а) или (б), строку **не убирает**: маска начинается с настоящего начала тревоги, поэтому `y_h = 1` известен. Убрать такие строки значило бы отобрать их по будущему (около 400 строк при h = 3).
- `y_h = 1`, если в единице начинается тревога в интервале `(t, t+h]`. Для каждого горизонта своя колонка.
  - Пример: в 14:00 тихо, тревога начинается в 15:30. Тогда `y_1 = 0`, `y_3 = 1`, `y_6 = 1`.
- **Базовая частота** — доля единиц в каждой колонке, то есть вероятность без всякой модели. С ростом h она растёт.
- **Тест корректности:** в каждой строке выполняется `y_1 ≤ y_3 ≤ y_6`.
- **Выбор горизонтов по базовым частотам.** Если для какого-то h частота около 0.9, задача почти тривиальна, и горизонт стоит уменьшить. Если единиц очень мало, метрики будут шумными. Решение записать в `DECISIONS.md`.
- **Доля окон с несколькими тревогами.** Среди положительных строк для h = 3 посчитать долю, где в окне два и более начала тревоги. Если она большая, бинарная цель теряет много информации, и это аргумент перейти к модели времени до события или к счётчику (см. «Вне MVP»).
- **Результат:** датафрейм с целевыми переменными, базовые частоты, доля окон с несколькими тревогами, число выброшенных маской строк.

### Этап 4. Бэктест и бейзлайны (до любых моделей) — выполнено

**Как сделано:** `backtest.py`, `models/baselines.py`, `metrics.py`, `evaluation.py`, `leakage.py`; решения и цифры — D18; отчёт — `reports/backtest_h3.md`; проверка утечки на реальных данных — `reports/leakage_check.json`, синтетическая — `tests/test_leakage.py`. Лучший бейзлайн — B1 (PR-AUC 0.676 на тесте). B2 хуже B0: число активных областей летом не измеряет волну (D18).

**Исходное задание:**
- **Бэктест.** Для каждого дня теста модель обучается на строках с `t ≤ начало_дня − h` (их метки уже полностью известны) и предсказывает этот день. У всех моделей одинаковый интерфейс `fit` / `predict_proba`. Валидация проводится той же процедурой на днях валидационного периода.
- **Горизонт — параметр конвейера**, для каждого h своя модель. В MVP сначала только h = 3.
- **Бейзлайны:**
  - **B0:** общая частота по train.
  - **B1:** частота по связке «единица × час суток» за последние 4 недели.
  - **B2 («волна»):** эмпирическая вероятность в зависимости от числа областей, которые сейчас под тревогой.
- **Метрики:** PR-AUC, ROC-AUC, Brier, log loss, калибровочная кривая.
  - Считаются по всем строкам вместе **и** по областям.
  - **Блочный бутстреп по дням обязателен:** единицы сильно скоррелированы (57% тревог совпадают по минуте с тревогой другой единицы), и эффективный объём выборки гораздо меньше числа строк.
- **Тест на утечку:** испортить все данные после `t` (перемешать или заменить шумом); прогноз в `t` не должен измениться ни на бит. Для слоя данных (`AlertHistory`) такой тест уже есть: `tests/test_history.py`. На этапе 4 его нужно расширить до признаков и прогноза. Ограничение такого теста: он портит готовый CSV и не видит утечек, которые создал сам источник, записывая события задним числом (выдуманные концы, D16). Такие случаи моделируются явно — через момент, когда событие стало известно, — и проверяются отдельными тестами.

**Готово, когда:** есть таблица метрик бейзлайнов на тесте с доверительными интервалами, и тест на утечку проходит.

### Этап 5. Признаки — выполнено

**Как сделано:** `src/alerts/features.py` (все признаки поверх `AlertHistory`, векторно), `src/alerts/geo.py` (соседство по границам районов из снимка датасета), решения — D19. Тревога без видимого отбоя активна не дольше 24 часов (по записям, таблица `data/seen.csv`). Строки с перерывом канала в последние 24 часа в модель не идут; счётчик за 7 дней масштабируется на наблюдаемое время. Сверх плана — соседние *единицы* (доля под тревогой, начала за 60 минут).

**Исходное задание:**

Все признаки — функции только от истории до `t`.

- **Своя единица:**
  - время с конца последней тревоги;
  - число тревог за 6 часов, 24 часа и 7 дней;
  - доля времени под тревогой за последние сутки.
- **Своя область:**
  - доля единиц под тревогой сейчас;
  - сколько единиц вошло в тревогу за последние 30 и 60 минут.
- **Страна:**
  - число областей с активной тревогой (включая Донецкую как вход, D06);
  - число новых тревог за последние 30 и 60 минут (индикатор начавшейся волны).
- **Соседние области:** есть ли в них сейчас тревога. Список соседства сверяется с геоданными.
- **Календарь:** час по Киеву, день недели.
- **Идентичность единицы:** категориальный `unit_id`.
- **Записи с флагом `uncertain`:** решить и записать, как они учитываются (по умолчанию — активны не дольше 24 часов). Правило причинное, его стоит реализовать внутри `AlertHistory` (D16).
- **Перерыв канала (D15):** счётчики с окном, которое задевает перерыв, занижены. Решить, нормировать ли их на наблюдаемое время (`AlertHistory.outage_seconds`).
- Все признаки строятся векторно для всех моментов сразу (методы `AlertHistory` принимают массив моментов), а не циклом по `t`.

### Этап 8. Проверка на свежих данных alerts.in.ua (после этапа 7) — выполнено

## Уроки из предыдущих решений (репозиторий Kizashi, прошлый поток отбора)

- В бейзлайне persistence была ошибка на единицу: прогноз строился по `T−1` вместо `T`. Из-за этого преимущество модели выглядело как +0.11 вместо реальных +0.03.
- Важность признаков по числу разбиений вводила в заблуждение, по gain картина была корректной.
- Монотонный признак «дни с начала данных» в тесте выходит за диапазон train. Модель экстраполирует его как константу, и это даёт смещение калибровки, а не настоящее знание.
- Авторы обрезали данные на реформе и не тестировали на последнем периоде. Наше отличие — работа с районным режимом и оценка на последних доступных данных.

## Вне MVP (если останется время)

- **Проверка на смене источника: API alerts.in.ua** — **токен получен, перенесено в этап 8.** Ниже — исходные соображения. Источники **не склеивать** (D02): модель обучена и «заморожена» на данных Vadimkin до 7 сентября, а на данных API считается отдельная проверка. Подавать в README отдельным разделом, не смешивая с основным тестом.
  - **Риски склейки:**
    1. У источника другая обработка: свои метки времени, свои правила для пропущенных отбоев (у Vadimkin конец «начало + 1 час»), своя логика уровней. Областная тревога может быть записана одной записью там, где у Vadimkin было несколько районных, и наоборот.
    2. Брать только тип тревоги `air_raid`; артиллерийские обстрелы и прочие типы в данные не включать.
    3. Названия и идентификаторы локаций отличаются, часть районов переименована, Киев устроен по-своему. Таблицу соответствия проверять вручную, не доверять сгенерированной ИИ.
    4. Общего периода с данными Vadimkin может не быть. Тогда расхождение источников нельзя измерить напрямую, и любое изменение метрик — смесь ухудшения модели и смены источника. Глубину истории API проверить в документации сразу после получения токена.
    5. Признаки в новом периоде считались бы по данным другого источника, а модель обучена на признаках из данных Vadimkin: если источник фиксирует больше или меньше тревог, сдвигаются признаки, а с ними и прогнозы.
    6. Проверяющие без токена эту часть не перезапустят. Сохранённую выгрузку класть в репозиторий только если это разрешают условия API.
  - **Процедура:**
    1. Сначала сверить источники без моделей: по каждой единице тревог в сутки, долю времени под тревогой, медианную длительность, профиль по часам, структуру клонов. Последние недели Vadimkin против первых недель API.
    2. Сопоставление локаций построить и вручную проверить на 10–15 районах.
    3. Бейзлайны считать на тех же данных API. Оценивать **относительно** («модель против бейзлайнов на одном источнике»). Абсолютные цифры и калибровка в этом сравнении ненадёжны.
    4. Первую неделю API отдать под разогрев признаков; бейзлайну B1 нужно 4 недели истории.
    5. Результат описать с оговоркой, что это проверка устойчивости к смене источника, а не продолжение основного теста.
- **Другие Telegram-каналы** (отклонено для MVP). Причины: волонтёрский канал `UkraineAlarmSignal` даёт только уровень областей; каналы ОВА — десятки разных форматов, без гарантии полноты и точности времени; мониторинговые каналы описывают траектории и угрозы, а не объявленные тревоги. **Единственное исключение:** если в закрепе или описании `air_alert_ua` указан переезд на новый канал с тем же форматом постов — тогда процессор или скрипт из 1б.4 можно запустить на нём. Проверить за 2 минуты.
- **Модель времени до события в дискретной форме (первый кандидат на улучшение).**
  - Одна модель вместо отдельной на каждый h. Она предсказывает `p_k` — вероятность того, что тревога начнётся именно в k-й час после `t`, при условии что в часы 1…k−1 она не началась. Номер часа k подаётся как признак.
  - Вероятность для любого горизонта: `P(старт в пределах h) = 1 − (1 − p_1)(1 − p_2)…(1 − p_h)`.
  - Плюсы: одна модель на все горизонты; вероятности автоматически монотонны по h; используется информация о том, когда внутри окна началась тревога.
  - Технически это та же бинарная классификация, LightGBM работает без изменений. Меняется форма данных: строки `(t, k)` идут до первого начала тревоги, после него обрываются (цензурирование).
- **Альтернативные целевые переменные:**
  - число тревог в окне — пуассоновская регрессия; естественно сочетается с процессом Хоукса;
  - доля окна, которую единица проведёт под тревогой — регрессия на отрезке [0, 1].
- **Посты об угрозах как признак.** Если в 1б.4 сохранён архив канала: предшествуют ли угрозы в одной единице тревогам в соседних. Считать строго по времени публикации поста.
- **Громады** как признак локальной активности в районе (D08).
- **Данные до реформы:**
  - Киев — единица, чей ряд реформа не затронула. Для него однородная история доступна с 2022 года;
  - проверить, можно ли склеить ряды на уровне области (сравнить частоты, длительности, профиль по часам до и после реформы);
  - добавить «климатологию» как признаки, считая её строго по данным до момента прогноза;
  - стекинг: предсказание областной модели как признак районной;
  - абляция: модель с этими признаками против модели без них.
- **Погода (Open-Meteo).** Только архив прогнозов (Historical Forecast, Previous Runs, Single Runs). Реанализ (Historical Weather) — это утечка.
- **Сводки Воздушных сил о числе запусков.** Публикуются утром о прошедшей ночи, признак нужно сдвигать на время публикации.
- **Двухвременной журнал событий** (время события и момент, когда о нём узнали; `AlertHistory` фильтрует по второму). Принципиальная замена пары `intervals` / `seen` (D21).
- **Процесс Хоукса на numba.**
- **Длительность текущей тревоги** как отдельная задача.
