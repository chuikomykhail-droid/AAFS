# Ревью этапа 8: Проверка на свежих данных alerts.in.ua

## 1. Резюме

Этап 8 выполнен методически грамотно и изолированно: данные API alerts.in.ua и датасета Vadimkin не склеиваются, замороженные модели обучаются строго на историческом ряде, а сопоставление 119 единиц выполнено без потерь благодаря нормализации апострофов и учету переименований. Главная содержательная находка — проверка утечки `knowledge_check` на периоде API слепа к ретроспективным правкам самого API (при отключенном процессоре считается `written = finished_at`), из-за чего 45 тревог со сдвинутым на полмесяца `updated_at` считались известными до момента их фактического обновления в базе. Логика объединения интервалов надежно защищает конвейер от двойного счета при разворачивании областных тревог, а триангуляция через волонтеров устойчива к фиктивным концам (`naive=True`), хотя множитель ×1.27 маскирует сильную региональную асимметрию запада и востока. Общий вердикт: **этап принят, критических блокирующих ошибок нет, найденные особенности должны быть зафиксированы в ограничениях**.

## 2. Находки

### S8-1. Разворачивание областных тревог создает дублирующие записи при наличии районных
- **Серьёзность:** существенно.
- **Уверенность:** проверено на данных.
- **Где:** `src/alerts/ingest/alerts_in_ua.py:112-116`, `DECISIONS.md` (D22).
- **Что не так и почему:** Единственная развернутая на районы областная запись (Николаевская область, id 270817, 2026-10-02 02:51:23 – 02:56:04) разворачивается на 4 района. Однако в исходном ответе API в этот же момент уже присутствовали отдельные районные записи для всех 4 районов (id 270818–270821) со временем 02:51:24/25 – 02:56:04. В результате в `recs` попадают по 2 экземпляра тревоги для каждого района.
- **Доказательство:** Скрипт `scratch-gpro/stage8/check_pipeline_intervals.py` выявил 4 пары перекрывающихся на 1–2 с записей в Николаевской области. В `recs` (до сборки интервалов) находится 9 записей вместо 5.
- **Последствие для результатов:** Последующий шаг `build_intervals` вызывает `merge_labels` / `spans.union`, которые объединяют перекрывающиеся интервалы единицы в один отрезок `[02:51:23, 02:56:04]`. Поэтому в признаках и целевой переменной двойного счета времени нет. Однако в сыром `recs` и статистике отчета `records: 14 389` эти 4 записи учтены дважды (фактически уникальных тревожных событий 14 385). При появлении в будущем других областных тревог без строгого совпадения времен это может искажать счетчики `n_records`.
- **Что сделать и сколько стоит:** В `load_alerts_in_ua` проверять, нет ли уже районных тревог в те же моменты, или выполнять дедупликацию перед добавлением развернутых записей. Оценка: ~30 минут. Перезапуск `run_all.py` не требуется (затрагивает только `scripts/api_check.py`). Справочные цифры не меняются.

### S8-2. Проверка утечки `knowledge_check` на периоде API игнорирует `updated_at`
- **Серьёзность:** существенно.
- **Уверенность:** проверено на данных и по коду.
- **Где:** `src/alerts/leakage.py:55, 63-74`, `src/alerts/processor.py:36-38`.
- **Что не так и почему:** В `processor.py` при `cfg['processor']['enabled'] = False` флаг `is_fake_end` отключается. В `leakage.py:55` строка `written = rec['next_start'].where(rec['is_fake_end'], rec['finished_at'])` превращается в `written = rec['finished_at']`. Это означает предположение, что любая закрытая тревога API стала известна ровно в момент `finished_at`. Однако в данных API 57 районных записей имеют `updated_at` позже `finished_at` более чем на 1 час (в среднем на 6.9 суток позже, до 18 суток), причем 55 из них обновлены пакетно 2026-09-30 18:32:00.
- **Доказательство:** Скрипт `scratch-gpro/stage8/check_late_updates_leakage.py` показал, что на срезе 2026-09-29 14:00 (за 28 часов до этой пачки) находилось 45 тревог целевых/входных единиц, у которых `finished_at <= cut`, но `updated_at > cut`. Функция `known_at` сочла их закрытыми до среза. Тест `knowledge_check` успешно прошел только потому, что опирался на `finished_at`.
- **Последствие для результатов:** Если эти записи были фактически добавлены или закрыты в базе API лишь 30 сентября, то наблюдатель в реальном времени 29 сентября не имел бы о них информации (или считал бы их открытыми). Тест `knowledge_check` не подтверждает отсутствие утечки ретроспективных правок базы API, а лишь тестирует механику построения признаков.
- **Что сделать и сколько стоит:** Внести оговорку в раздел ограничений отчета `api_check.md` и `DECISIONS.md` (D22). Для строгой проверки можно параметризовать `written = max(finished_at, updated_at)`. Оценка: 15 минут на документацию или 1 час на код.

### S8-3. Множитель триангуляции ×1.27 маскирует региональную неоднородность
- **Серьёзность:** существенно.
- **Уверенность:** проверено на данных.
- **Где:** `src/alerts/api_check.py:125-138`, `DECISIONS.md` (D22).
- **Что не так и почему:** Вывод о том, что API фиксирует в 1.27 раза больше тревог для той же реальности, получен усреднением по всем 24 областям (`r_src / r_vol = 1.59 / 1.25 = 1.27`). Но в тыловых 18 областях отношение равно 1.75 / 1.45 = 1.21, а по 7 западным областям рост у пары источников составил ×6.83 при росте у волонтеров всего ×1.70 (отношение ×4.01).
- **Доказательство:** Расчет в `scratch-gpro/stage8/check_triangulation.py`. В августе у Vadimkin на западе были единичные тревоги (деление на малое число), а в сентябре–октябре активность налетов сместилась вглубь страны.
- **Последствие для результатов:** Единый коэффициент ×1.27 создает ложное впечатление равномерного сдвига масштаба по всей стране, тогда как на западе произошел структурный скачок плотности тревог. При этом проверено: фиктивные концы волонтеров (`naive=True`, 5.0% записей) вообще не влияют на метрику `starts_per_oblast_day`, так как она использует только `start`.
- **Что сделать и сколько стоит:** Дополнить текстовый комментарий в `reports/api_check.md`, указав, что сдвиг масштаба неоднороден по регионам. Оценка: 10 минут.

### S8-4. Незрелость истории B1_live и малый объем бутстрепа по дням
- **Серьёзность:** мелочь.
- **Уверенность:** проверено на данных и по коду.
- **Где:** `scripts/api_check.py:176-184`, `DECISIONS.md` (D22).
- **Что не так и почему:** В D22 указано, что B1_live имеет «7–23 дня истории». Фактически B1_live запускается с 2026-09-26, а данные API начинаются с 2026-09-12. То есть в первый день оценки B1_live имеет ровно 14 дней истории, а в последний — 29 дней. При штатном окне B1 в 28 дней (`b1_window_days: 28`) модель почти половину периода недополучает объем скользящей истории. Кроме того, 16 дней — крайне малый объем выборки для кластерного бутстрепа по дням.
- **Доказательство:** Расчет дат в `scratch-gpro/stage8/check_window.py`. Доверительные интервалы для разностей с B1_live широкие (например, при h=6 разность LGBM − B1_live составляет +0.006 [−0.008, +0.017], пересекая ноль).
- **Последствие для результатов:** Выводы о статистической значимости преимущества моделей над свежим бейзлайном при h=3 (+0.021 [+0.002, +0.036]) находятся на грани чувствительности из-за малого числа дней.
- **Что сделать и сколько стоит:** Уточнить формулировку в `DECISIONS.md`: «14–29 дней истории». Оценка: 5 минут.

### S8-5. Оценка в «23 дня» включает неполные сутки
- **Серьёзность:** мелочь.
- **Уверенность:** проверено на данных.
- **Где:** `scripts/api_check.py:161`, `reports/api_check.md`.
- **Что не так и почему:** В заголовках таблиц указано «23 days». Фактический интервал теста — с `2026-09-19 00:00:00` по `2026-10-11 08:00:00`, то есть ровно 22 дня и 8 часов (22.33 суток). Дата 11 октября представлена лишь 8 утренними часами.
- **Доказательство:** Значение `cfg_a['data_end'] = '2026-10-11T08:00:00+00:00'`.
- **Последствие для результатов:** Ошибки в расчете нет, строки отбираются корректно, но текстовое обозначение «23 дня» может восприниматься как полные 23 суток.
- **Что сделать и сколько стоит:** Уточнить в отчете: «22.3 дня (23 календарные даты)». Оценка: 5 минут.

## 3. Проверено и в порядке

1. **Сопоставление 119 локаций:** Полное взаимно-однозначное соответствие (119 из 119). Нормализация символов апострофа (U+2019 у Vadimkin против U+0027 в API) предотвратила потерю 3 районов (454 записи). Киев корректно сопоставлен по названию `м. Київ` при типе `oblast`. 3 переименованных района (Берестинский, Шептицкий, Владимирский) успешно сопоставлены через `geo.renames`.
2. **Семантика окна `month_ago`:** На данных подтверждено, что API обрезает историю строго по `finished_at` (все закрытые записи имеют `finished_at >= req - 30 days`). Тревоги, начавшиеся до окна, но завершившиеся внутри него (64 записи), приходят целиком с исходным `started_at` без обрезки. Открытые тревоги передаются независимо от давности старта.
3. **Открытые тревоги на момент скачивания:** Все 60 незавершенных тревог получают временный конец `requested_utc`, который строго позже `data_end` (08:00 UTC). В рабочем периоде они остаются открытыми и штатно ограничиваются `max_open_hours: 24`.
4. **Фильтрация типов и уровней:** Корректно отсеяны артиллерийские обстрелы (282) и уличные бои (1). Уровни `city` и `hromada` (1 644 записи) исключены в полном соответствии с правилами охвата D05/D08.
5. **Временная согласованность с волонтерским рядом:** Кросс-корреляция часовых профилей начал дает четкий пик при сдвиге 0 часов. Медианная разница между совпадающими началами составляет −15 с у Vadimkin и −19 с у API. Это исключает ошибки в часовых поясах (UTC vs Kyiv time).
6. **Чистота замороженных моделей:** Никакие гиперпараметры, пороги или признаки не подбирались по данным API. Признаки рассчитываются изолированно через `AlertHistory`.
7. **Воспроизводимость и соответствие README:** README честно документирует, что сырые файлы API не входят в репозиторий из-за лицензионных ограничений и для воспроизведения с нуля требуется собственный токен.

## 4. Открытые вопросы

1. **Внутренние алгоритмы alerts.in.ua:** Неизвестно, по каким критериям сервис объединяет городские и районные тревоги и закрывает ли он зависшие тревоги принудительно (в данных есть 101 тревога длительностью более 24 часов).
2. **Истинная природа пакета обновлений 2026-09-30 18:32:** Из-за отсутствия ежедневных снимков API невозможно восстановить, какие именно значения полей (`finished_at`, `alert_level` или `notes`) имели 55 записей до момента их обновления 30 сентября.
