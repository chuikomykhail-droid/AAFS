Ревьюер: Claude (независимый). Скрипты и выводы: `reviews/scratch/stage8/` (`a01`–`a10`, `b01`, `b02`, `common.py`; промежуточные прогнозы в `out/`). Всё запускалось из корня с `PYTHONPATH=src`. Файлы проекта не менялись, к API не обращался, токен не открывал.

## 1. Резюме

Код этапа 8 корректен там, где его можно проверить механически. `b01_frozen.py` воспроизвёл все цифры `reports/api_check.md` до третьего знака, утечки в коде не нашёл. Окно `month_ago` обрезается по `finished_at`, поэтому выбор `work_start` и разогрева верен. Сопоставление 119 из 119 и разворачивание областных записей тоже в порядке.

Слабые места — в выводах и процедуре:
- Главный вывод README для основного горизонта («при h = 3 замороженная модель сохраняет преимущество над B1, обновляемым на API») неустойчив. Он держится на правиле старта B1_live, выбранном после того, как результат был виден. Когда у B1_live больше истории, преимущество уходит в шум; по дням оно положительно в 7 из 16 дней.
- Запланированное повторное скачивание в понедельник не добавит понедельник: из-за `data_end = min(requested_utc)` период сократится на сутки.
- Адаптер молча игнорирует поле `alert_level` (yellow/red). Оно делит записи примерно 65/35 и дрейфует внутри периода. В D22 и PLAN о нём ничего нет.
- Проверка утечки на API по построению сводится к обрезке по срезу. Поздних правок со стороны источника она не видит.
- Множитель «×1.27» верен по направлению, но его величина зависит от агрегации (1.1–1.3).

Вердикт: зона рабочая, но формулировки README/D22 надо смягчить, а процедуру повторного скачивания исправить до понедельника.

## 2. Находки

### S8-1. Вывод «преимущество при h = 3 сохраняется» не устойчив к выбору старта B1_live
- **Серьёзность:** критично: меняет вывод README для основного горизонта. **Уверенность:** проверено на данных.
- **Где:** `README.md:106-108`, `DECISIONS.md:635`, `PLAN.md:243`; правило «неделя истории» — `scripts/api_check.py:176-181`. В журнале ошибок № 26 сказано, что B1_live добавлен после разбора результата.
- **Что не так.** Известно, что B1_live незрелый (7–22 дня истории). Новое здесь в том, что незрелость работает в пользу модели, а значимость при h = 3 держится на одном произвольном пороге. Правило «не меньше 7 дней истории» выбрано после того, как результат замороженных моделей был виден, и чувствительность к нему не проверялась.
- **Доказательство:** `b02_live.py`, бутстреп 1000 по дням, тот же seed. Разность PR-AUC LGBM − B1_live при h = 3 в зависимости от минимальной истории B1_live:

  | История B1_live, не меньше | Дней | LGBM − B1_live | LR − B1_live |
  |---|---|---|---|
  | 1 день | 22 | +0.023 [+0.007, +0.037] | +0.002 [−0.016, +0.018] |
  | 4 дня | 19 | +0.020 [+0.003, +0.033] | −0.005 |
  | **7 дней (отчёт)** | 16 | **+0.021 [+0.002, +0.036]** | −0.003 |
  | 10 дней | 13 | +0.019 [**−0.004**, +0.034] | −0.004 |
  | 14 дней | 9 | +0.011 [**−0.017**, +0.028] | −0.010 |

  По 16 дням отчёта LGBM лучше B1_live в **7 из 16** дней, средняя дневная разность **+0.000**. Ранговая корреляция «разность ~ длина истории B1_live» равна −0.35. Jackknife по дням даёт интервал t [+0.000, +0.041]: нижняя граница совпадает с нулём. Положительная объединённая разность при нулевой средней дневной означает, что выигрыш идёт от ранжирования **между** днями: модель видит «волну» по признакам, а B1_live — статичная таблица. Внутри дня при h = 3 модель B1_live не превосходит.
- **Для контраста.** При h = 1 вывод устойчив: при любом старте от +0.041 до +0.055, все нижние границы выше нуля, положительна в 13 из 16 дней, jackknife [+0.032, +0.072]. При h = 6 преимущества нет (так и написано).
- **Последствие.** Фраза README «зберігає перевагу при h = 1 і 3 — того самого порядку, що й на основному тесті» верна для h = 1. Для h = 3 преимущество пограничное и не доказано, если дать B1_live больше истории.
- **Что сделать.** Переформулировать README, D22 и PLAN: «устойчиво при h = 1; при h = 3 пограничное (+0.021, нижняя граница +0.002; при ≥ 10 днях истории B1_live интервал включает 0)». Добавить в `api_check.md` таблицу чувствительности к старту. Это 15–30 минут. `run_all.py` перезапускать не нужно, справочные цифры не меняются.

### S8-2. Повторное скачивание в понедельник не добавит понедельник, а сократит период на сутки
- **Серьёзность:** существенно: процедура из PLAN и D22 делает обратное заявленному, а план — выполнить её в день дедлайна. **Уверенность:** проверено на данных (симуляция в памяти по коду `read_raw`/`api_config`, без сети).
- **Где:** `src/alerts/api_check.py:33-37` (`data_end = min(requested_utc).floor('h')`, `start = (max(requested_utc) − 30 d).ceil('D')`), `src/alerts/ingest/alerts_in_ua.py:52`; обещание — `PLAN.md:243`, `PLAN.md:259` («так добавится понедельник»), `DECISIONS.md:643`.
- **Что не так.** После объединения по `id` записи, которые есть только в первом скачивании, сохраняют воскресное `requested_utc`. Это тревоги, закончившиеся между «воскресенье − 30 дней» и «понедельник − 30 дней». Поэтому `min(requested_utc)` остаётся воскресным, `data_end` не двигается, а `work_start` сдвигается на сутки вперёд.
- **Доказательство:** `a08_redownload.py`. Второе скачивание моделируется на +24 и +34 часа: окно по `finished_at` и слияние ровно как в `read_raw`. Только в первом скачивании остаются 513 и 720 id. `work_start` 12.09 → **13.09**, `warmup_end` 19.09 → 20.09, `data_end` остаётся **2026-10-11 08:00**. Часовых моментов прогноза 536 → **512**. Новые понедельничные тревоги попадут после `data_end`, то есть под маску (в), и в оценку не войдут.
- **Что сделать.** Считать `data_end` как минимум по uid последнего запроса каждого uid, а `work_start` — от последнего скачивания. Это около 15 минут; после правки нужен перезапуск `scripts/api_check.py` (2–3 мин, после скачивания). Заодно выводить сравнение двух скачиваний по `id`: изменившиеся `started_at`/`finished_at` и пропавшие id. Это единственный способ измерить поздние правки источника (см. S8-4).

### S8-3. Поле `alert_level` (yellow/red) игнорируется и нигде не описано
- **Серьёзность:** существенно. **Уверенность:** факты проверены на данных; влияние на выводы — гипотеза.
- **Где:** `src/alerts/ingest/alerts_in_ua.py:91-127` (поле не используется), в списке полей `PLAN.md:252` его нет, D22 о нём молчит. Нарушено правило 1 («сначала `value_counts()`»). В ответах есть и другие поля вне документации: `country`, `location_title_en`, `location_oblast_uid`.
- **Факты** (`a03_level.py`, `a05_level_time.py`):
  - у районных `air_raid` 9 280 yellow и 4 888 red; у Киева 201 из 217 записей yellow;
  - доля red по неделям падает: 0.46 → 0.44 → 0.31 → 0.31 → 0.27;
  - по областям доля red меняется от 5% (Ровенская) до 84% (Днепропетровская) и 100% (Закарпатская);
  - внутри одного объявления уровни почти не смешиваются: из 10 237 групп «область × минута начала» смешанных 55;
  - из 101 записи длиннее 24 часов 91 имеет уровень red;
  - примечание к одной записи: «ukrainealarm: … (Дронова загроза, жовтий)».

  Похоже, что yellow — тревога из-за дронов, red — из-за ракет или авиации. Это гипотеза: документация без сети недоступна.
- **Последствие.** Цель на API смешивает два класса сигналов, и их соотношение дрейфует внутри периода. У Vadimkin уровня нет, поэтому неизвестно, оба ли класса публиковал официальный канал. От состава зависит и триангуляция:

  - только red — 1.24, ×0.29;
  - вместе — 5.42, ×1.27;
  - у Vadimkin в августе — 3.40.
- **Что сделать.** Описать поле в D22, найти его смысл в документации API и добавить в `api_check.md` разбивку числа записей и начал по уровню. Это 30–60 минут, перезапуск `run_all.py` не нужен.

### S8-4. Проверка утечки на API по построению проверяет только код; README говорит шире
- **Серьёзность:** существенно. **Уверенность:** проверено по коду и на данных.
- **Где:** `src/alerts/processor.py:107-110`, `src/alerts/leakage.py:55`; `README.md:109` («Перевірку на витік на періоді API пройдено»), `DECISIONS.md:638-640`.
- **Что не так.** При `processor.enabled: false` все `is_fake_end` ложны, и `written = finished_at`. Тогда `known_at(cut)` — это просто обрезка по срезу с открытыми тревогами до «срез + 1 с». Обе проверки («знание на момент среза» и «порча будущего») проверяют одно свойство: признаки не читают записи после среза. Класс D21, запись позже своих меток времени, для API не моделируется вовсе: правки и удаления на стороне источника по одному снимку не видны.
- **Доказательство:** `a10_known_at.py`: `known_at == обрезка` → `True`, 8 620 записей, 31 открытая (как в отчёте).
- **Новое по известным 57 поздним `updated_at`** (`a02_updated.py`, `a06_semantics.py`):
  - гипотеза «эти тревоги висели открытыми до пачки 30.09 18:32» опровергается: у всех 55 записей пачки следующая тревога того же района началась **до** обновления (от 1 до 187 стартов), а одновременно открытых записей одной локации в API нет (4 исключения в Донецкой области);
  - значит, реальный конец лежал не позже следующего старта района. Худший случай — строки той же единицы с `t` между `finished_at` и следующим стартом: **62 из 42 004** строк при h = 3 (0.15%), 35 моментов, медианный зазор 0.8 ч. Количественно это пренебрежимо;
  - что именно менялось в пачке, по одному снимку не определить: прежней версии записи нет.
- **Что сделать.** В README заменить формулировку, например: «перевірка коду на витік пройдена; пізні правки з боку джерела одним знімком перевірити неможливо, оцінка зверху — 0.15% рядків». Это 5 минут. Реальную проверку даёт сравнение двух скачиваний (S8-2).

### S8-5. «API фиксирует в 1.27 раза больше начал»: направление устойчиво, величина — нет
- **Серьёзность:** существенно для вывода D22; на модели не влияет. **Уверенность:** проверено на данных.

  - **«Одна линейка» в августе расходится с Vadimkin по уровню.** Отношение «волонтёры / Vadimkin»: Львовская ×61, Волынская ×17, Днепропетровская ×6.5, Харьковская ×3.3. Видимо, волонтёры там считают локальные тревоги (гипотеза). Днепропетровская и Харьковская дают 29% всех волонтёрских начал.

## 3. Проверено и в порядке

- **Окно `month_ago`** обрезается по `finished_at`, а не по началу (`a01_raw.py`): максимум «запрос − конец» 29.988 сут, «запрос − начало» до 30.79 сут; есть записи, начавшиеся 10.09 13:44 и 11.09 00:57. Тревоги, начавшиеся до окна, но закончившиеся в нём, присутствуют. `work_start` = 12.09 00:00 позже любого края окна (11.09 08:45–08:59), так что состояние на `work_start` полное.
- **Разогрев.** 7 дней равны самому длинному окну признаков (`starts_7d`). Строк со `since_end` = NaN в API-части **0** (`a09_features.py`).
- **`data_end`** = 08:00 раньше самого раннего запроса (08:45) и `meta.last_updated_at` (08:42). Оценивается 23 календарных дня (19.09–11.10; последний день неполный, 8 ч), у B1_live — 16.
- **Сопоставление.** Несопоставленных районных названий API нет. «м. Київ» встречается только с типом `oblast` (217 записей). Три переименования взяты из границ, соответствие один к одному.
- **Разворачивание областных записей.** Единственная запись по Николаевской области (02.10 02:51:23–02:56:04) дублирует 4 районные записи с точностью до секунды. Объединение по единице не даёт лишних начал, двойного счёта нет. Луганская область и Крым разворачиваются в пустоту.
- **Слияние по `id`.** Харьковская область скачана дважды: 2 373 id, `updated_at` и `finished_at` совпадают. NaT в `updated_at` нет. Пар «та же локация, то же начало, разные id» нет.
- **Артефакты обработки.**
  - записей ровно 3 600 с — 0, ровно 1 800 с — 1;
  - самый длинный промежуток без событий — 3.74 ч, меньше порога 6 ч;
  - записей длиннее 24 ч — 101, из них 80 в Донецкой области (только вход); маска (а) закрывает 0.45% целевых единице-часов;
  - одновременные концы в ≥ 3 областях в одну секунду (388 моментов, 22% записей) похожи на общенациональные отбои (пример — 15.09 16:44–17:09, западные области), а не на массовое закрытие «зависших» (интерпретация — гипотеза).
- **Замороженные модели** (`b01_frozen.py`, LightGBM на 2 потоках) воспроизвели все таблицы `api_check.md` до третьего знака, включая B1_live. Обучение идёт на строках Vadimkin с `t ≤ data_end − h`, гиперпараметры взяты из `tuning_h*.json`. На API ничего не обучается, кроме B1_live.
- **Часовой пояс.** Лучший сдвиг 0 ч, медианный лаг −19 с — воспроизведено. Утверждение D22 о профиле по часам подтверждается и на уровне областей: Vadimkin (авг) против API (сен–окт) — 0.63, волонтёры (авг) против волонтёров (сен–окт) — 0.69.
- **Сдвиг признаков.** Счётчики в API в 1.3–1.5 раза выше, базовая частота при h = 3 — 0.34 против 0.255. Это согласуется с D22.
